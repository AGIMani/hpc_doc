# 使用须知

!!! danger "先读这一页再上机"
    这一页列出的规则是集群**已经生效的技术限制**。
    违反其中任何一条通常不会损坏服务器，但会让你的任务无法启动或直接被终止。

## 为什么必须通过 Slurm 使用 GPU

集群限制了普通登录会话对 GPU 的访问。这意味着：

* 在 SSH 终端里直接运行 `nvidia-smi`：**报错** `Failed to initialize NVML: Unknown Error`
* 直接运行 `python train.py`：**看不到 GPU**，PyTorch 会回退到 CPU 或报 `CUDA unavailable`
* 通过 `srun` / `sbatch` / `salloc` 提交的任务：**正常访问分配给它的显卡**

!!! info "这是刻意设计的"
    早期版本里，任何登录用户都可以直接占用 GPU，导致「有人占了卡但调度器不知道」，
    其他人在 `squeue` 里看不到任何任务却申请不到显卡。
    设备隔离的目的就是让**调度器的记录等于真实占用**。

登录终端里能做什么：

| 可以 | 不可以 |
|---|---|
| 编辑代码、传数据、装环境 | 跑训练、推理、任何需要 CUDA 的程序 |
| `sinfo` / `squeue` / `sacct` 查询 | 用 `nvidia-smi` 查看显卡占用 |
| `sbatch` 提交、`srun` 起交互任务 | 用 `tmux` 挂一个脚本让它长期占卡 |

## 资源申请的默认值与上限

| 项目 | 默认 | 上限 / 说明 |
|---|---|---|
| 任务时限 | 不写 `--time` 时为 **1 小时** | 最长 **7 天**，到时强制终止 |
| 内存 | 每个 CPU 默认 **4096 MiB**，可用 `--mem` 覆盖 | 节点可调度约 `2,000,000 MiB` |
| GPU | 必须显式申请 `--gres=gpu:N` | 单个任务最多 8 张（整机） |
| CPU | 按 `--cpus-per-task` 分配 | 128 个逻辑 CPU |

!!! danger "任务超过时限会被杀死"
    长训练必须把 `--time` 写足，并且**在脚本里定期存 checkpoint**。
    时限到点 `slurmctld` 直接发信号终止任务，没有任何缓冲时间。

!!! warning "`--mem` 限制的是主机内存"
    整卡独占模式下，显存由任务自己管理。
    `--mem=64G` 表示允许这个任务用 64 GiB **主机内存**，和显存没关系。
    申请了 8 张卡并不会自动给你 640 GB 内存。

## 不要绕过调度器

除了直接开终端跑程序，以下入口同样受限制，**不要试图用它们占卡**：

| 入口 | 说明 |
|---|---|
| `crontab` 定时任务 | 定时任务同样运行在受限会话中，拿不到 GPU |
| 网页终端 | 属于普通登录会话，同样受限 |
| 常驻后台服务 | 不要用 `nohup` 等方式长期占卡，请用 `sbatch` |

正确做法：**用 `sbatch` 提交，用 `--begin` 延时启动**。

```bash
# 想「今晚 22 点开始跑」
sbatch --begin=22:00:00 train.sh

# 想「每小时跑一次小任务」：交给 Slurm 队列
sbatch --array=0-23 --time=00:30:00 hourly.sh
```

## 磁盘与数据安全

!!! danger "服务器不是网盘"
    服务器可能宕机、磁盘可能损坏、任务可能被误删。请务必：

    1. **代码托管到 GitHub / GitLab** 等平台，别只放在服务器上；
    2. **训练过程定期存 checkpoint**，并考虑同步一份到本地或对象存储；
    3. **重要数据不要只留一份**。

查看磁盘占用：

```bash
df -h                 # 各分区剩余空间
du -sh ~/* | sort -h  # 家目录里各子目录大小，从大到小
```

!!! warning "家目录写满会影响所有人"
    把家目录写满会影响整个集群，所有人都提交不了任务。
    请把大数据集放到数据盘，并及时清理。

## 环境与依赖

* **不要** 在系统 Python 里 `pip install`。用 uv 虚拟环境，见 [Python 环境管理](uv.md)。
* **不要** 自行 `apt install` / 升级 NVIDIA 驱动或 CUDA —— 驱动升级需要同时处理
  Fabric Manager 版本，做错了这台机器上所有卡都不能用。需要新软件请联系管理员。
* CUDA Toolkit 已经装好，路径在 `/usr/local/cuda`（默认版本）以及带版本号的目录下。

## 调试与正式任务的分工

| 场景 | 建议方式 |
|---|---|
| 改代码、试语法、验证数据路径 | 登录终端里做，**不碰 GPU** |
| 需要真实跑一次前向 / 反向 | `srun --gres=gpu:1 --pty bash` 申请一张卡调试 |
| 正式训练、长时间实验 | `sbatch` 提交，写好 `--time` 与日志输出 |
| 一次跑几十组超参 | `sbatch --array` 任务组 |

!!! info "不要在登录终端里跑重活"
    登录终端里的进程不受 Slurm 资源限制，如果跑满 CPU 或内存，
    会拖慢调度服务本身，影响所有人的任务。

## 遇到问题怎么办

1. 先查 [常见问题](faq.md)，尤其是 `NVML: Unknown Error`、`CUDA out of memory`、
   任务一直 `PENDING` 这几类；
2. 用 `scontrol show job <JOBID>` 看任务的真实排队原因；
3. 仍然解决不了，把以下信息一起发给管理员：

```bash
scontrol show job <JOBID>          # 任务详情
sinfo -N -l                        # 节点状态
squeue -u "$USER"                  # 自己的队列
tail -n 50 logs/<JOBID>.err        # 报错日志
```
